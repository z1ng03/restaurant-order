# Техническое задание: Telegram-интеграция Restaurant Order

**Версия:** 2026-11-02. **Статус:** исходный код интеграции подготовлен, полноценная сборка и работа с реальной PostgreSQL требуют проверки в целевой среде.

## 1. Исходная архитектура (проверено по проекту)

Restaurant Order состоит из `backend` (Express, TypeScript, Prisma ORM, PostgreSQL, REST API) и статического `frontend` (HTML/CSS/JavaScript). Отдельные роли сотрудников обслуживаются модулем `auth`, клиенты — `clientAuth` и `clientAccount`. `checkout.service.ts` переводит оплату KASPI_QR в демонстрационный `PAID` и создаёт чек **в той же транзакции**; `waiter.service.ts` переводит наличные в `PAID` только по подтверждению официанта. `receipts.service.ts` сохраняет неизменяемый снимок, `delivery.service.ts` доставляет по e-mail и Telegram и записывает `receipt_dispatches`. В `client_telegram_links` уже есть привязка через `client_telegram_link_tokens`; исходный webhook принимал `/start <token>` только из личного чата. GET `/api/orders/:orderId/receipt` принимает подтверждённый аккаунт, допустимую роль сотрудника либо секрет kiosk-сессии соответствующего заказа. Это основание для гостевого сценария.

## 3. Пользовательские сценарии

**Зарегистрированный пользователь.** Открывает бота, отправляет `/login`, переходит по кнопке на `FRONTEND_BASE_URL/profile.html#telegram_login=...`. При отсутствии активной сессии сайта проходит обычную авторизацию, после чего нажимает «Подтвердить вход в Telegram» в профиле. При успешной привязке бот получает доступ к истории заказов и сохранённым чекам. Альтернативно остаётся исходный сценарий «Привязать Telegram» из профиля: сайт создаёт deep link, а бот обрабатывает старый одноразовый токен. Автоотправку можно включить отдельно; выход из бота отзывает связь.

**Гость.** Оформляет и оплачивает заказ из терминала. Открывает чек: новая кнопка «Получить в Telegram» запрашивает ссылку с установленным `X-Kiosk-Session-Token`. Если оплата ещё не подтверждена (включая CASH), запрос отклоняется. Открытие выдаваемой `https://t.me/<bot>?start=g_...` из личного Telegram-чата приводит к доставке сохранённого чека. Ссылка одноразовая; после доставки она недействительна. Секрет терминала и номер заказа отдельно не дают права на чужой чек.

## 5. Новые HTTP API

`POST /api/orders/:orderId/receipt/telegram-link` — при валидном client bearer / staff роли / kiosk secret и `PAID` возвращает `201 { deepLink, expiresAt }`. Ошибки: 403 invalid kiosk token; 404 чужой заказ; 409 ещё не оплачен; 503 не настроен Telegram; 429 rate limit. Не принимает `chat_id` и не выдаёт информацию по голому `orderId`.

`POST /api/client-account/telegram/confirm-bot-login` — клиентский bearer, тело `{ "token": "l_..." }`; результат `200 {linked:true}`. 410 при истёкшем/использованном токене, 409 при занятом чате, 401 при отсутствии авторизации. Пользователь подтверждает связь после входа на сайт.

`PATCH /api/client-account/telegram/auto-receipts` — клиентский bearer, строго `{ "enabled": true|false }`; возвращает `{ autoReceipts }`. Требует действующую привязку. Старые маршруты `/api/client-account/telegram/link`, `DELETE /api/client-account/telegram`, `/api/client-account/orders/:orderId/receipt/telegram` остаются.

`POST /api/integrations/telegram/webhook` — Telegram webhook с секретным заголовком. Принимаются только события из личного чата, отправитель должен совпадать с идентификатором чата. Обрабатываются команды `/start`, `/login`, `/orders`, `/receipts`, `/logout`, `/help`; callback `menu`, `login`, `logout`, `help`, `orders:<page>`, `order:<id>`, `receipts:<page>`, `receipt-order:<id>`; произвольная строка не даёт прямой доступ к данным.

## 6. БД и транзакции

Миграция `20261102000000_telegram_bot` добавляет `client_telegram_links.auto_receipts DEFAULT FALSE`, `telegram_bot_login_requests` (хеш, чат, TTL, used_at), `telegram_receipt_claims` (хеш, заказ, TTL, used_at), `telegram_processed_updates` (уникальный update_id) и `telegram_auto_deliveries` (одна запись на чек; статус, попытки, отложенный повтор, lease). Индексы поддерживают выборку очереди и поиск временных записей. В таблицах токенов хранится только SHA-256. Гостевой токен резервируется атомарно до отправки; при сбое отправки резерв снимается, при успехе токен считается потреблённым. Несколько обновлений webhook не обрабатываются повторно. Отдельный воркер выбирает PENDING/RETRY и истёкшие PROCESSING, а по результату обновляет SENT/RETRY/FAILED. Пять попыток, экспоненциальная задержка. Сбой после фактического успеха Telegram, но до записи SENT, теоретически допускает повтор сообщения (Telegram не поддерживает сквозную exactly-once транзакцию); повторного списания денег или создания чека нет.

## 7. Информационная безопасность и ограничения

Пароли и токены бота хранятся только в `.env`, не отправляются пользователю в чате. В боте не принимаются введённые пароли. Вход требует подтверждённой авторизации на сайте. Для чека каждый запрос проверяет принадлежность заказа. Для гостевых ссылок доступ доказывается текущей kiosk-сессией либо правами аккаунта. Используется ограничения запросов к HTTP-эндпоинтам, встроенный webhook-secret, атомарное погашение токенов, экранирование выводимого текста не требуется, поскольку Telegram использует обычный текст без `parse_mode`. `autoReceipts` выключен по умолчанию. Режим webhook предполагает публичный HTTPS-адрес; polling намеренно не добавлен, чтобы не создавать конкурирующих источников событий. Для полноценной безопасности развертывания необходимы отдельные секреты, HTTPS, брандмауэр и ограничение доверенных proxy.

В `tests/unit/telegramBot.test.ts` проверяется парсинг команд. В `tests/integration/telegramBot.test.ts` предусмотрены тесты с отдельной PostgreSQL базой и подменяемым TelegramSender: меню, дедупликация, отклонение поддельного отправителя, отсутствие доступа к гостевому чеку без kiosk-secret, выдача оплаченного чека по одноразовому токену, истечение, неоплаченный CASH, авторизация и повторное использование login-токена, история заказов, чека, выхода, отказ транспорта, повторное использование после сбоя, outbox и отсутствие повторной оплаты. Существующие тесты сохранены. Проверки должны запускаться по инструкции `TELEGRAM_SETUP.md`, затем в реальном тестовом боте проверяются ссылки, кнопки и доставка. Скриншоты настоящего бота должны сниматься только в работающей среде после настройки вебхука. Текущая среда не предоставила доступных пакетов npm, тестовой PostgreSQL и действующего публичного Telegram webhook; сборка, интеграционные тесты и доставка требуют проверки на целевой машине. Нельзя трактовать синтаксическую проверку как подтверждение работоспособности.
